# Heterogeneous Fleet Configuration Guide

This guide explains how to configure and evaluate a heterogeneous multi-agent fleet in the Warehouse environment. It covers the YAML configuration parameters, the mechanical effects they introduce to the simulation, and how to interpret the resulting evaluation dashboards.

---

## 1. Defining a Heterogeneous Fleet

Heterogeneity is controlled via the `heterogeneity` section in your YAML configuration file. When enabled, it allows you to assign specific mechanical constraints to individual agents in the environment array.

Here is an example configuration (`configs/heterogeneous_small.yaml`):

```yaml
environment:
  env_id: rware-tiny-2ag-v2
  max_steps: 500

heterogeneity:
  enabled: true
  energy_weight: 0.05
  agents:
    - speed: 1.0                # Agent 0
      capacity: 2
      battery_capacity: 40.0
    - speed: 0.5                # Agent 1
      capacity: 10
      battery_capacity: 100.0
```

*   `enabled: true` — Turns on the constraints wrapper. If missing or `false`, the environment acts strictly homogeneous (no arbitrary limits).
*   `energy_weight` — (Optional) Floating metric scaling the reward penalty derived from moving / acting limits.
*   `agents` — An array mapping parameter sets 1-to-1 onto the agents generated by `env_id` (so our 2-agent example above needs exactly 2 entries).

---

## 2. Explanation of Parameters

Each parameter directly restricts the mechanical allowances for that agent:

### `speed` (Range: 0.0 to 1.0)
Mechanically interpreted as the probability the agent successfully executes their action. 
*   A speed of `1.0` means the agent's action executes normally 100% of the time.
*   A speed of `0.5` means there is a 50% chance the agent's action is forcibly intercepted and overwritten with a `No-op` (rest/idle command). They are literally slower on average over time.

### `capacity` (Integer)
Defined as the **consecutive-carry limit**. 
Once an agent picks up a load, a counter tracks their consecutive steps carrying that object. If their turn counter exceeds their `capacity`, any action they try to make *other than un-loading (pick/drop toggle)* will be forcefully blocked and converted into a `No-op`. The agent cannot do anything else until they unpack/drop the load somewhere.

### `battery_capacity` (Float)
Sets the total energy budget for the agent. 
Actions cost energy: 
*   **Move / Turn:** 1.0 units
*   **Load / Unload:** 2.0 units
*   **Idle / No-op:** 0.5 units

Once an agent's `battery_capacity` reaches `0.0`, they enter a **"dead"** state. Every action they attempt for the remainder of the episode is forcefully converted to a `No-op`, paralyzing them.

---

## 3. The `energy_weight` Parameter

The `energy_weight` (default `0.0` if omitted) introduces a reward shaping penalty tying energy efficiency directly into the agent's native RL reward stream. 

At every step, the `HeterogeneousRWAREWrapper` calculates the active energy cost (0.5 to 2.0) used by the agent, multiplies it by the `energy_weight` scaler, and strictly deducts that value from the agent's native step reward. 

For example, carrying a heavy load with poor action scaling via a `0.05` weight effectively shaves a fixed cost overhead off the 1.0 base reward granted upon finishing jobs.

## 4. Reading the Evaluation Dashboard

Executing `run_evaluation_demo.py` will run a snapshot of simulation metrics and output `evaluation_summary.png`. This contains 4 independent subplots:

1.  **Throughput (Tasks Completed):**
    Tracks the total number of items delivered successfully to the goal per episode. 
    > [!NOTE]
    > **A blank/flat-zero throughput panel can be a perfectly legitimate result.** Our `configs/heterogeneous_small.yaml` test restricts Agent 0 to almost zero capacity/battery, and Agent 1 to 50% speed. Agents severely restricted mechanically may chronically fail to ever deposit a single reward package within the 500 max steps.

2.  **Energy Efficiency (Energy Per Task):**
    Measures the aggregated energy budget consumed during the episode divided by the amount of completed tasks. Highly efficient cohorts use less total energy to clear tasks. If *no* tasks are completed during a run sequence, this subplot organically logs an "undefined limit" text message, skipping math exceptions organically. 

3.  **Task Completion Time (Episode Lengths):**
    A frequency histogram showing the total step lengths dynamically before episode termination or arbitrary truncation.

4.  **Per-Agent Workload (Avg Reward Contribution):**
    A core bar chart evaluating group dynamics. It tracks the cumulative reward individually credited back to each agent, mapping averages out to visualize exactly who is shouldering the largest mechanical workload and if dead agents actively halt downstream flow.
